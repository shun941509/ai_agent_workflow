## Agent ZIP 내보내기 · 2026-11-26

Chrome의 1440px 화면에서 **Agent 내보내기 → ZIP 내려받기**를 확인했다. 자동 저장이 실패한 상태에서 대출 한도를 3권에서 5권으로 바꾸고 **변경 적용**을 누른 뒤 7권으로 다시 편집했다. ZIP에는 5권 원문이 들어갔다. 선택을 해제한 문서는 사용 단계와 다시 연결할 경로가 남았고, 원문은 빠졌다. 같은 화면의 기존 JSON 내보내기에서 편집 중인 7권 원문을 선택해 받을 수 있었다. [브라우저 시험](../tests/agent-export-browser.ts)

같은 편집기에서 MCP가 처음에는 모두 선택 해제되는지 확인했다. 서버 주소가 바뀌면 새 주소를 다시 선택해야 내려받을 수 있었다. 내려받은 ZIP에서 선택한 원격 연결의 세 클라이언트 설정, 수동 연결 안내, 공통 Skill 원문과 Claude용 참조를 대조했다. MCP를 모두 제외한 ZIP에는 서버 설정이 없었고 두 ZIP 모두 루트 실행 스크립트와 `runtime/` 폴더가 없었다. [브라우저 시험](../tests/agent-export-browser.ts)

Git 저장소가 없는 임시 폴더에 압축을 풀고 Codex CLI에서 새 작업을 시작했다. 시험 식별자는 채팅 입력에서 생략하고 ZIP의 지침에만 넣었다. Codex가 응답으로 그 식별자를 돌려줬다. Codex는 신뢰한 시험 폴더에서 선택한 MCP 주소와 허용 도구를 읽었다. 실제 모델 시험은 `node --import tsx tests/agent-export-live.ts codex`로 실행하며 마지막 인자로 `claude` 또는 `opencode`도 지정할 수 있다. [실제 모델 시험](../tests/agent-export-live.ts)

Claude Code에서 로컬 모의 모델로 보낸 첫 요청에 `AGENTS.md`의 시험 식별자가 포함돼 `CLAUDE.md`의 참조가 작동하는 것을 확인했다. 프로젝트 설정의 환경 변수에서 시험용 토큰을 읽고 로컬 MCP 서버에 연결하는 것도 확인했다. 실제 Claude 모델은 로그인 세션이 없어 호출하지 않았다.

OpenCode 2.4.1에서 같은 방식으로 내보낸 폴더를 열었다. 로컬 모의 모델에 보낸 요청에서 공통 지침의 제목과 Skill 식별자를 확인했고, Skill 목록에서 `.agents/skills/`의 원문도 확인했다. OpenCode는 `opencode.json`에서 선택한 MCP 서버를 읽고 로컬 모의 서버에 초기화와 도구 목록을 요청했다. [OpenCode 설정 호환 문서](https://opencode.ai/docs/migrate-v1/#mcp-servers)

타입 검사, 프로덕션 빌드, 전체 자동 시험 223건을 통과했다. 대상 시험에는 출시 판단 설계의 하위 작업에 연결한 자료·출력 필드·사용자 선택, 승인·거절, 권한 재검사, Skill 부속 파일의 바이트 보존이 포함된다. 브라우저는 최종 프로덕션 빌드에서 ZIP 다운로드와 같은 편집기의 JSON 내보내기 경로를 검증했다. 이전 전체 브라우저 시험에서는 모델을 끈 시험 서버가 지점 조사 실습의 업무 범위 판정을 완료하지 못해 대상 선택 전에 중단됐다. ## 실제 OpenAI 모델 시험 결과

2026년 11월 21일, 당시 기록에서 ‘24시간 키’로 부른 프로젝트용 OpenAI API 키를 서버에 설정하고 기본 작업실을 재시작했다. `gpt-6-astra` 모델 정보를 조회하는 요청은 HTTP 200을 반환했다. 첫 실행은 `credit_balance_exhausted`로 종료됐다. 크레딧 지급 후 같은 입문 실습에서 “회원증을 처음 만들 때 무엇을 가져가나요?”라고 묻자 “회원증을 처음 만들 때는 신분증을 가져오시면 됩니다.”라는 실제 답변과 `completed` 상태를 확인했다.

같은 날 Windows에서 별도 웹 서버, 실행 워커, 도서관 MCP 서버를 시작했다. 임시 데이터베이스를 사용하는 이 환경에서 같은 모델로 설계 제안·수정과 일곱 실습을 실행했다. 당시 `pnpm test:live`의 8개 시나리오가 모두 통과했다. 이후 두 전문가 실습을 학습자가 직접 정책과 게시 여부를 결정하도록 바꿨다. 변경한 두 시나리오를 실제 모델로 다시 실행해 모두 통과했다. [실제 서비스 인수 시험](../tests/live-service.ts)

**설계 제안·수정** — 빈 설계에서 회의록 입력, AI 작업, 답변 전달 블록을 생성했다. 처음 생성한 설계를 실행하면 담당자가 정해진 항목만 출력됐다. 담당자가 없는 항목을 ‘미정’으로 표시하도록 처음 수정했을 때도 홍보 항목이 빠졌다. 완료 기준을 고쳐 담당자가 정해진 항목에는 이름을 적고, 담당자가 아직 없는 홍보 항목도 포함해 담당자를 ‘미정’으로 표시하도록 했다. 그런 다음 같은 원문을 다시 실행했다. 결과에는 확정된 ‘자료집 23권’과 담당자 ‘민걙’, 별도 항목인 ‘다음 달 홍보 담당자는 정해지지 않았음’과 담당자 ‘미정’이 함께 나왔다. 수정 후 격리된 작업실에서 세 버튼을 한 흐름으로 눌렀다. 수도 질문에는 어떤 Agent를 만들지 한 번 물었다. “회의 메모에서 결정 사항을 뽑아 줘”로 보충하자 **회의 메모 입력 → 결정 사항 추출 → 결정 사항 전달**과 연결선 4개가 보였고, 프로젝트는 적용을 누른 뒤 생성됐다. **AI 설계 → 변경 제안 받기**에서 담당자 표기를 변경하고 적용 전에는 저장된 그래프가 그대로인지 확인했다. 적용 후 **질문 실행**에 담당자가 정해지지 않은 인쇄 결정을 입력하자, 실제 모델의 결과 표에 ‘안내문 17부 인쇄’와 ‘배정 대기’가 같은 행에 표시됐다.

편집기에서 같은 ID를 가진 블록이 두 팀에 있을 때, 한 팀 안에서 받은 변경 제안이 루트에 적용되는 문제를 재현했다. 수정 후에는 현재 팀만 변경됐고, 전체 Workflow로 검사한 결과와 오류가 있는 팀·블록이 적용 전에 표시됐다. 데스크톱 Chromium에서 취소, 적용, 한 번의 실행 취소, 다른 팀의 설정 보존을 확인했다. 이 사례에서는 두 팀에 동일한 응답 조건을 만들기 위해 모델 응답을 고정했다. [편집기 브라우저 시험](../tests/editor-focus-proposal-browser.ts)

실제 서버 워커와 모의 모델로는 후속 질문의 첫 실행과 재시도에 전달된 이전 문답을 비교했다. 수정 전에는 재시도에서 금요일 회의 결정이 사라졌다. 수정 후에는 처음 질문할 때의 회의 결정을 참조했고, 그 뒤에 입력한 문답과 범위 밖 부탁은 전달되지 않았다. [재시도 회귀 시험](../tests/agent-scope-run.test.ts)

프로덕션 빌드와 타입 검사, 자동 시험 206개, 생성·편집·실행 관련 데스크톱 Chromium 시험 4개 묶음이 통과했다. 실제 모델 시나리오 `new-agent-intent`, `proposal`, `agent-scope`도 모두 통과했다.

## 재현 명령

실제 모델의 예약 도구 선택과 승인·실행을 확인하려면 프로젝트 루트에서 `node --import tsx tests/live-tool-approval.ts`를 실행하세요. 작업실 실행기와 같은 모델 설정을 사용합니다. 시험은 임시 SQLite 저장소와 로컬 도서관 MCP를 열고 시험 계정으로 ‘달빛 산책’을 호수관에서 수령하도록 요청합니다. 승인 전에는 예약이 0건이고, 같은 승인을 다시 전송하고 워커 두 개를 실행한 뒤에는 예약과 영수증이 각각 1건이어야 합니다. 새 요청을 거절하면 예약 수가 그대로여야 합니다. [실제 모델 통합 시험](../tests/live-tool-approval.ts)

공통 검증 명령과 브라우저 실행 조건은 README에서 확인한다. [검증](../README.md#verification)

실제 모델 시험 중 일부만 다시 실행하려면 PowerShell에서 `$env:STUDIO_LIVE_CASES = 'proposal,intermediate'`처럼 시나리오 ID를 쉼표로 구분해 지정한 뒤 `pnpm test:live`를 실행하세요. 필터를 설정한 뒤 전체 시나리오를 시험하려면 `Remove-Item Env:STUDIO_LIVE_CASES`로 필터를 해제하고 `pnpm test:live`를 다시 실행하세요. 필터를 설정하지 않았다면 `pnpm test:live`만 실행하세요.
